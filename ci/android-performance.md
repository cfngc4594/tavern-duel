# Android 整局性能验证

后续的法术、粒子和结算优化及整局对照见 [Android 法术与结算性能](android-fx-performance.md)。

## 测试条件

- 真机为 V2509A，Android 16，Mali-G1-Ultra MC12。测试包均使用 Godot 4.7.1 ARM64 Release、OpenGL ES Compatibility 和同一个本地签名。原版基于 `cf27e6f`，只加入同一套基准采集钩子。
- 固定种子 `5834`，后手，正常对局。从冷进程启动开始采集，跑过开场、换牌、硬币、抽牌、法术、战吼、攻击、死亡特效和结算。驱动器调用实际游戏动作，动画和回合时钟使用游戏原来的时间。各版均在第 9 回合以生命值 `[24, -2]` 获胜，35 条驱动动作的类型、牌和回合一致。
- 手机面板在每局开始前关闭，Android 保持唤醒。通过 ADB logcat 记录连续 `process_frame` 的墙钟间隔和游戏脚本阶段。黑屏时 SurfaceFlinger 的游戏层有缓冲记录，物理呈现间隔直方图全为零。下文 FPS 均为 Godot 循环速率，GPU 内存为 Godot 渲染内存计数。
- 各版依次运行，电池起始温度为 32.5、34.3、33.5、33.4、34.4 °C。每版一局，温度和驱动缓存状态有差异。Release 静态内存监控返回零，该指标无有效样本。

## 变更与原因

| 路径 | 变更 |
| --- | --- |
| 棋盘静态网格 | CI 将 52 个静态网格离线烘成 305,187 字节的 Godot 资源，检查格式、顶点通道、索引、包围盒和往返加载。动态网格和缺少预生成数据时走原构建路径。原版棋盘创建 513 ms，第三轮 442 ms。 |
| 卡面与肖像 | 卡面默认去掉仅用于像素审计的上传后 GPU 回读和 SHA256。首次烘焙每张牌回读从 4 次降到 2 次，费用变化时从 2 次降到 1 次。保留源回读和缓存绑定。圆形肖像只在兼容绘制首次使用时生成，避免启动时为原生卡牌重复建立纹理。肖像阶段从 285 ms 降到 176 ms。 |
| 开场硬币 | 加载期准备静态网格、动画时长与激活点、纹理、着色器和音频，复用准备结果。硬币实际播放时才分配演出视口并启动动画。第三轮真机准备耗时 113 ms，发牌 `flow` 阶段峰值从 153.16 降到 90.98 ms。 |
| 首帧与渲染 | 首次棋盘和空间视口绘制完成后开放对局时钟。第三轮首次绘制等待 1.11 s 计入加载，加载门从引擎时间 9.68 s 移到 11.36 s。Android 上离屏棋盘从 2637×1215 降到 1953×900，空间视口从 4× 改为 2× MSAA。第一轮的 MSAA 设置曾被旧场景初始化覆盖，第二轮修正。 |
| 逐帧脚本 | 稳定目标高亮跳过网格 GPU 回读，姿态、网格或可见性变化时更新。复用棋盘粒子的尺寸、颜色和 UV 数据，减少无变化时的列表分配。手牌网格统计移到创建时，点击测试复用布局计数，空间场景减少重复相机同步。 |
| 传输合成 | 仅在值变化时更新镜像变换、材质、权重和可见范围等属性，保留 RGB 传输合成。真机绘制调用中位数基本持平。 |
| 胜利烟火 | 两个高负载烟火尾迹在每个工作线程独占各自粒子，主线程等待完成后读取，省去逐粒子复制和字段合并。原密度下胜、负、平 315 帧的本地状态、事件、RNG 和网格校验值一致。 |
| Android 装饰粒子 | 环境粒子采用原发射密度的 40%，点击棋盘触发的交互效果继续用原密度。两个胜利烟火尾迹采用 25% 发射密度，保留烟火主体。不可见的召唤粒子继续模拟，只省略网格构建。第三轮对手回合的棋盘推进平均 4.41 ms，原版为 9.94 ms。 |
| Android 法术渲染目标 | 战斗特效的捕获、遮罩和光晕目标按一半尺寸渲染，像素面积约四分之一。保持相机和模糊半径，降低屏幕特效遮罩的采样成本，烈焰风暴的颜色与透明度通道共用提取后的网格。 |

## 采用第三轮

第三轮的整局循环速率为 27.47 FPS，原版为 22.50。P99 从 416.82 降到 233.22 ms，至少 250 ms 的帧从 63 降到 39。结算阶段 P95 从 534.04 降到 245.66 ms。法术最大帧间隔约 920 ms，结算最大约 1.10 s，仍未达到平稳 30 FPS。

第四轮尝试让光晕复用已捕获的源纹理，玩家法术阶段绘制调用中位数由 330 降到 319。该轮整局有效 FPS 降到 25.85，P95 升到 88.23 ms，玩家法术阶段 P95 升到 337.89 ms。第四轮起始电池温度比第三轮高 1 °C。工作区保留第三轮的战斗捕获实现和第四轮的可选诊断计时。

验证覆盖了 48 项无头回归、APK 签名与原始资源字节检查、真机完整动作序列及正常结算。恢复第三轮战斗捕获实现后，重新通过了战斗特效分辨率与环境粒子回归。黑屏条件下的测量覆盖应用的渲染循环，实际屏幕呈现节奏和降低画质后的可见细节仍待亮屏检查。

## 复跑

在独立的 Android 导出预设中设置 `command_line/extra_args="-- --android-match-benchmark --android-match-profile --startup-timing"`，导出、签名并安装。使用 `adb logcat` 保留每局从 `MATCH_BENCH_BEGIN` 到 `MATCH_BENCH_END` 的记录。运行 `python3 ci/analyze_android_match.py baseline.log candidate.log` 生成逐阶段分布、峰值帧和动作序列，分析器会拒绝帧号不连续的记录。日常试玩包可省略全部基准参数。

## 独立场景基准

用正式主场景运行 `--android-match-benchmark --android-match-quit --android-scenario=<名称>`，并用 `--android-match-output=<可写路径>` 保存完整记录。Android 诊断包可将这些参数放在导出预设的 `--` 后。`--android-scenario-suite` 可替代单场景参数。每个进程运行一个场景，成功后在应用内部记录下一项，按下表顺序循环。完整对局继续使用原来的整局参数。

| 名称 | 测试内容 |
| --- | --- |
| `idle` | 正常静止棋盘、冻结水粒子、冻结透射镜像同步、恢复正常。各采集 180 帧，并检查棋盘、空间和透射视口的尺寸与更新模式。冻结组用于估算开销，使用各自的静止快照。 |
| `opening-draw` | 固定种子的真实开场与第一回合抽牌。用同种子重开，分别记录重开、发牌和抽牌，核对手牌、牌库及触发次数。 |
| `heavy-spell` | 通过正式规则触发火球术和火焰冲击，各记录首次和重复触发，校验生命与法力。可加 `--android-scenario-particle-profile` 采集粒子状态推进、几何循环及网格上传的分项诊断耗时。 |
| `terminal` | 通过正式胜负入口触发两次胜利，分别采集英雄死亡、结算及 `screen.show()` 首次构建。 |

首次触发指本进程完成正式加载后的第一次触发，Android 驱动缓存可能来自之前的进程。无头运行仅用于验证行为和日志格式。用 `python3 ci/analyze_android_match.py <日志>` 查看逐阶段帧间隔、脚本分项和场景校验结果。真机保持物理面板黑屏时，这些帧时间属于应用循环。

## Mac 后台渲染复跑

用 `zsh ci/run_macos_background.zsh --path <已导入的项目目录> --resolution 1440x810 -- --android-match-benchmark --android-match-profile --android-match-quit --android-match-seed=5834`。启动器为 Godot 4.7.1 创建临时后台应用，保持 Compatibility 渲染、窗口尺寸和视口更新，同时让测试窗口透明且不接收输入。终端输出用 `MACOS_BENCHMARK_MODE background` 标记。性能 A/B 的两组均使用同一种启动方式。后台测试记录应用和渲染阶段耗时，屏幕刷新与漏刷用前台显示测试验收。导出和逻辑回归继续用 `--headless`。
